# Panel console, runtime TrueType fonts, and sound modules

Panel output is standard on both Pico families. USB serial remains available.
One firmware per processor contains all four NES-compatible panel drivers;
a saved settings record selects the screen at boot. There is no separate
firmware build for each screen and no executable driver loader.

## Live fonts

The emulator rasterizes actual TrueType outlines on the Pico. The default
face is Terminal Sans, derived from Lato Regular, at 14 pixels. Terminal Mono,
derived from JetBrains Mono, is also included. Character spacing uses each
font's advances and bearings. Lines wrap by pixel width.

At the USB console, press Ctrl-], release it, then:

| Key | Action |
| --- | --- |
| `f` | Switch between the bundled font faces |
| `+` | Increase the font size by one pixel |
| `-` | Decrease the font size by one pixel |
| `s` | Show status, including face, size, cache and errors |
| `t` | Export the generated glyphs for `tools/font_capture.py` |

These commands do not reach Unix. Font changes reflow the visible text and
keep the guest running. Requests are queued until the current panel transfer
and font generation finish. Font selection does not erase/program flash.
The boot setting `readable` selects 14 pixels; `compact` selects 11 pixels.
Live changes are temporary until the next reboot.

The rasterizer reads sfnt, cmap format 4, hmtx, loca and quadratic glyf
outlines, with nonzero winding fill and antialiasing. It generates one glyph
scanline per turn, services USB/disk/clock during selection and reflow, and
caches printable ASCII in 4 KB of RAM. It does not execute TrueType hinting
programs or perform OpenType shaping. The console is seven-bit ASCII, not a
Unicode text engine. A proportional face is suitable for ordinary console
text; use the monospace face when column alignment matters.

Sizes 14–16 pixels are hardware checked with both faces. The API accepts
8–20 pixels subject to the fixed cache/outline limits. A request that exceeds
the cache is refused with status `-5` and regenerates the previous font.
It never silently overwrites another RAM allocation.

`tools/font_pack.py` prepares the source fonts: it subsets printable ASCII,
decomposes composite glyphs into simple quadratic TrueType contours, and
writes `outputs/truetype_assets.pmi`. **It does not generate pixels.** The
runtime renderer is `outputs/truetype.pmi`. The fonts' source files and OFL
notices are in `fonts/source/`. Derived subsets are renamed to respect
reserved font names. Regenerate/check with:

```text
py -3 -m pip install fonttools
py -3 tools/font_pack.py
py -3 tools/font_pack.py --check
```

`tools/term_font.py` forwards to this preparer. To inspect the actual glyphs
generated by a connected board, `tools/font_capture.py --port COM7 --out
work/font` exports a PNG and raw snapshot; it requires pyserial and Pillow.
Its `--exercise` option checks live face/size changes and oversized-request
rejection. Acquire the normal board lease before running it.

## Resident screen profiles

| Setting | Controller | Landscape pixels | NES wiring |
| --- | --- | --- | --- |
| `lafvin` (default) | ST7796 | 480 × 320 | SPI0 SCK2, MOSI3, CS5, DC6, RESET7 |
| `display-pack2` | ST7789 | 320 × 240 | SPI0 SCK18, MOSI19, CS17, DC16, backlight20 |
| `ili9341` | ILI9341 | 320 × 240 | SPI1 SCK10, MOSI11, MISO12, CS13, DC16, RESET17 |
| `hx8357d` | HX8357D | 480 × 320 | Same SPI1 pins as ILI9341 |
| `none` | USB serial only | — | No display pins initialized |

ILI9341 backlight connects to 3V3. Follow the NES hardware notes for panel
power and the HX8357D SPI selection. HX8357D commands use a slower SPI clock;
pixel transfers switch divider without emitting a probe byte during RAMWR.
The shared driver handles each processor's DMA request-field layout.

`outputs/panel.pmi` exposes `PanelBegin`, `PanelStart(x,y,w,h,pixels)` and
`PanelPoll`. Pixels are RGB565; the caller retains the buffer until completion.
The terminal uses one scanline, not a full framebuffer. The demo uses the
same rectangle API and centers its 320 × 200 image on the selected panel.
Terminal painting yields while the guest graphics device owns the screen.

Build the normal emulator with the canonical IDE executable:

```text
py -3 tools/output_build.py --target rp2040 --compiler PATH/TO/PureMetalForge.exe --out work/pdp2040.uf2
py -3 tools/output_build.py --target rp2350 --compiler PATH/TO/PureMetalForge.exe --out work/pdp2350.uf2
```

Build without a hardware lease; use the normal lease/uploader for flashing.
The 2026-10-26 [ready images](images/README.md) include these features. Firmware-only downloads update an existing installation without downloading the disk packs again.
The existing `tools/term_build.py` filename wrapper remains supported for
RP2350. `tools/demo_build.py` builds the optional graphics/sound demo.

## Saved settings

```text
py -3 tools/output_config.py --target rp2040 --panel lafvin --font readable --out work/settings.uf2
py -3 tools/output_config.py --target rp2350 --panel display-pack2 --font compact --out work/settings.uf2
```

Upload the small settings UF2 through the normal uploader, or write its
companion `.bin` through the IDE's named `PDP11 outputs` storage region.
It contains only one settings sector. It does not replace firmware or disk
packs. The setting takes effect after reboot. Use `--reset` to restore defaults.

The protected sector is at flash offset `0x3F000` on RP2040 and `0x4F000` on
RP2350. The compiler's FlashRegion metadata prevents program overlap. It is
outside the Unix packs and RP2350 radio area. The versioned `P11O` record
contains panel/audio/font IDs and a checksum. Erased/legacy data selects
LAFVIN, silent audio and readable font. A recognized corrupt record falls
back to serial-only output and reports config status `-1`.

## Audio modules

The common sound producer generates signed mono 16-bit PCM at 48 kHz,
including console BEL and the demo's four voices. Silent output is standard.
Audio transport is selected at build time to avoid reserving radio/PCM RAM
in every image; the saved setting enables the linked backend at boot.
A requested backend that was not linked reports status `-2`.

| `--audio` | Linked backend |
| --- | --- |
| `silent` | No PCM ring or radio stack |
| `bluetooth` | SDK A2DP/SBC backend; runtime peer address from settings |
| `plugin` | `outputs/audio_plugin.pmi`; supplied example is a **silent** PCM drain/meter |

A custom module implements `OutputSinkBegin()` and `OutputSinkPoll()`, and
calls `OutputAudioRead(destination, sample_count)`. The producer, guest
registers, bell and panel do not need changes. A PWM/I2S/DAC transport can
replace the example; no such physical driver is claimed by the example.
Reads account for consumed samples, peak/nonzero values and overwritten data.

For Bluetooth, build with `--audio bluetooth` and create settings with
`--audio bluetooth --speaker AA:BB:CC:DD:EE:FF`. Keep the resulting personal
settings private. Connection uses the existing SDK and can wait up to 45
seconds; its status is reported. Pairing keys are not automatically written
to a disk or flash sector. The radio firmware must already be installed.
The current RP2040 Mini-Unix pack overlaps the radio blob at `0x100000`, so
the builder refuses that combination. Non-radio custom audio is supported
with that pack. This is a storage-layout restriction, not a chip restriction.

Guest memory stays at 56 KB on RP2040 and 152 KB on a standard RP2350.
RP2040 retains its 124-block overlay. RP2350 uses 248 file-overlay blocks with
silent output, 242 with the example PCM module, or 208 with Bluetooth;
its separate 112-block swap area remains. The live font workspace accounts
for six blocks compared with the earlier 254-block serial firmware. PSRAM
builds retain their existing guest memory and 36-block fallback overlay.

## Validation scope

LAFVIN panel output and Unix boot have run on both actual boards, at 200 MHz
RP2040 and 150 MHz RP2350. Runtime TrueType captures are byte-identical across
the two processors for the checked faces/sizes. Live changes preserve a guest
file and return to the same original glyph bytes after an oversized request.
The other three resident screen drivers compile and use the NES initialization
sequences, but their physical screens have not been validated in this PDP-11
session. Bluetooth audio has not been listened to in this session; PCM meter
checks do not establish audible speaker playback.
